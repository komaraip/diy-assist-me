Introduction
DIY activities such as cooking, repair, assembly, and crafting are increasingly learned through web-based tutorials instead of printed instructions. This is important in Indonesia because online access has become a major channel for reaching instructional content: DataReportal reports 230 million internet users and 80.5% internet penetration in Indonesia at the end of 2025 [1]. However, access to online content does not automatically mean that the interaction is accessible or usable. The WebAIM Million 2026 report found detected WCAG 2 failures on 95.9% of the top home pages [2], while Human I/O frames situationally induced impairments as temporary limits on the input, output, or attention channels available to a user [3]. In DIY contexts, these limits often appear when users must divide their hands, attention, and vision between a physical task and the digital tutorial.
Most tutorial websites assume that users can easily return to the screen, tap buttons, scroll, or type in a search box while following instructions. That assumption becomes problematic when a user is holding tools, mixing ingredients, assembling components, or handling materials that make direct device contact inconvenient, dirty, unsafe, or disruptive. The usability issue in this study is therefore not the absence of tutorial content, but the friction that occurs when a touch-centered interface must be used in a hands-busy situation. Voice-driven navigation is examined as a possible way to reduce this mismatch while keeping the visual tutorial available on screen.
Prior work indicates that speech interaction can be embedded in web experiences and used to improve access-oriented interaction, including voice-command augmentation, voice-enabled websites, and speech-recognition-based web prototypes [4], [5], [6]. At the same time, VUI research shows that voice input is not automatically more usable than touch input; its success depends on discoverability, command clarity, feedback, recognition reliability, and recovery from misunderstanding [7], [8], [9]. This makes an empirical comparison necessary. The study must measure not only whether voice commands work technically, but also whether they improve performance and perceived usability in a realistic tutorial task.
Existing systems such as browser voice assistants, context-aware voice browsing, and intelligent web navigation agents demonstrate that spoken commands can support web interaction [10], [11], [12]. Related work on instructional video navigation also shows that voice can help users pause, rewind, repeat, or locate specific instruction segments while performing complex tasks [13], [14]. Nevertheless, the setting of this thesis is more specific: a structured DIY tutorial website composed of step cards, materials, images, search functions, and navigation controls. Unlike video-only systems or general-purpose voice assistants, this study evaluates a focused set of web-native commands designed for tutorial navigation during hands-busy DIY activity.
The prototype therefore provides two comparable interaction modes on the same tutorial content: conventional touch navigation and web-native voice-driven navigation. The touch condition uses visible controls such as next step, previous step, materials, search, and tutorial overview. The voice condition triggers the same actions through spoken commands, including opening a tutorial, navigating steps, controlling scrolling, searching keywords, repeating instructions, toggling the voice assistant, and recording interaction logs. The comparison focuses on task completion time, task success, SUS usability scores, speech-recognition accuracy, command success rate, recovery effort, and observed usability problems. SUS is included as the subjective usability instrument because it produces a short, standardized post-condition score that can be completed after both modalities without changing the task flow. It is paired with behavioral logs and voice-specific metrics so that the evaluation does not rely only on self-reported perception.
The objective of this research is to evaluate whether a constrained set of voice commands can help mitigate situational impairments in DIY instructional tasks. The contribution is twofold: first, a web-native prototype that integrates voice controls into a structured tutorial interface; second, an empirical evaluation that compares voice and touch navigation under controlled hands-busy task conditions. The findings are expected to clarify when voice navigation is beneficial, when it introduces new friction, and what design implications should guide accessible instructional websites.
RQ1: How does web-native voice-driven navigation compare with conventional touch navigation in supporting task performance and perceived usability during DIY instructional tasks?
RQ2: How reliable is browser-based voice interaction in DIY instructional tasks, based on speech-recognition accuracy, command success rate, and recovery effort?
RQ3: What usability problems and design implications emerge when voice navigation is used to mitigate hands-busy situational impairments in DIY tutorial use?
The study is deliberately scoped to several limitations. The prototype uses a fixed set of English voice commands rather than open-ended multilingual conversation. It is also evaluated on a browser configuration that supports web speech recognition and in a quiet or low-noise environment. Therefore, the findings should be interpreted as evidence for controlled hands-busy DIY tutorial use, not as proof that the prototype will perform equally well in unsupported browsers, offline conditions, multilingual command use, or noisy workshop and kitchen environments.

Related Works
Related studies on voice-driven web interaction show that speech can be used to control browser functions, augment existing web pages, and support navigation based on page context. Firefox Voice demonstrates an open and extensible browser-based voice assistant for web actions [10], while accessibility-focused work on website augmentation shows how spoken commands can be added to improve interaction with existing sites [4]. Context-based voice browsing and WebNav further emphasize that voice navigation becomes more reliable when the system understands page state, interface elements, and user intent [11], [12]. Research on geographic web navigation also illustrates how domain-specific command vocabularies can support voice-based web interaction [15].
Other related works examine voice interaction as part of web inclusivity and accessible web systems. Co-design research on voice-based conversational AI and web augmentation highlights the role of participatory design in making voice interaction useful for diverse users [16]. Voice-enabled e-commerce and voice-controlled portfolio systems similarly show how speech recognition, command mapping, and interface feedback can be combined in web prototypes [5], [6]. These studies are relevant because they demonstrate the feasibility of voice interaction on the web, but most of them focus on general accessibility, browsing, or demonstration systems rather than a controlled comparison between voice and touch navigation in a DIY tutorial task.
Instructional-task research provides a closer context for this thesis. Zhao et al. studied how users employ voice interaction to navigate instructional videos while performing complex physical tasks, showing that people often need to revisit or control instructions without disengaging from the task [13]. RubySlippers extends this line of work by supporting content-based voice navigation for how-to videos [14]. These studies strongly support the need for hands-free instructional control, but their primary object is video navigation. A structured tutorial website introduces a different interaction problem because users must navigate discrete steps, material lists, page regions, search results, and fallback controls.
VUI and conversational-interface studies clarify why voice control must be evaluated carefully. A systematic review of VUI usability identifies recurring concerns around user experience, recognition reliability, and interaction design [7]. VORI proposes that voice user interfaces should be tested for interactability, including whether the system recognizes commands, responds usefully to errors, and helps users understand what they can say [9]. A meta-analysis of VUI guidelines also emphasizes feedback, transparency, context awareness, and recovery from failure [8]. Conversational web patterns add a related perspective by showing that web-based conversation needs clear interaction structure rather than open-ended speech alone [17].
Multimodal interaction research supports the design choice of combining speech with visual tutorial content rather than replacing the screen entirely [18]. Speech is appropriate for short commands, while the visual interface remains important for reading detailed instructions, confirming the current step, viewing images, and checking materials. Web implementation studies also indicate that accessibility and performance must be considered together in web applications, including React-based and progressive web contexts [19], [20]. For this reason, the prototype treats voice as an additional navigation layer over the same structured tutorial content, not as a separate interface with different information.
Usability-measurement research also informs the evaluation design. The System Usability Scale is widely used as a concise instrument for perceived usability [21], and validation work shows that SUS can also be applied to voice user interfaces [22]. SUS is selected instead of a longer or feature-specific questionnaire because this study requires a brief, technology-agnostic score that can be administered after each condition without creating excessive respondent burden. However, perceived usability alone is insufficient for this study because users may rate the system positively even when commands fail, or negatively even when tasks are completed quickly. A/B testing literature provides the logic for comparing interface alternatives through defined metrics, controlled tasks, and structured result analysis [23]. This thesis adapts that comparison logic into a within-subject design so that each participant experiences both touch and voice conditions.
From these related works, the first gap is contextual. Prior research has examined general web voice assistants, accessibility-oriented augmentation, voice-enabled websites, and instructional video control, but less attention has been given to structured DIY tutorial websites used while users are physically occupied. The second gap is empirical. Several systems show that voice interaction is technically feasible, yet they do not always compare voice and touch interaction using the same participants, matched task materials, and counterbalanced order. Without this comparison, it is difficult to determine whether voice navigation offers measurable benefit over conventional touch controls.
The third gap concerns measurement. Many studies discuss usability or voice-system behavior, but a hands-busy DIY setting requires both usability and interaction-reliability measures. Task completion time, task success, SUS, recognition accuracy, command success, recovery effort, and observations are needed together to explain whether voice input reduces friction or simply creates a different form of effort. The fourth gap concerns methodological control. Browser-based speech recognition may be affected by microphone quality, ambient noise, browser behavior, and network-dependent recognition services [24], so the testing environment and technical disruptions must be documented carefully.
This research addresses these gaps by building a focused DIY tutorial web prototype and evaluating it through a controlled within-subject comparison of touch and voice navigation. The study is positioned between accessibility-oriented voice web research and instructional-task research: it takes the hands-free need from instructional contexts, applies it to structured web tutorials, and evaluates the result with both usability and speech-reliability metrics. The expected contribution is therefore not only a prototype, but also empirical evidence about how web-native voice navigation performs when users face situational impairments during DIY tasks.

Methodology
Research Design
This study uses a controlled within-subject design to compare touch-based and web-native voice-driven navigation on the same DIY tutorial prototype. Interaction modality is the independent variable, while the primary outcomes are task completion time, task success, SUS, and voice-specific reliability measures. The paired design reduces between-participant variation, and AB/BA counterbalancing is used to control order and learning effects [23].
Research Flow
The research flow moves from literature review and prototype design to tutorial preparation, participant recruitment, counterbalanced testing, data cleaning, and paired analysis. This sequence keeps the prototype scope, metrics, and analysis aligned with the research questions and related works.

Prototype and Materials
The prototype is a browser-based DIY tutorial website that presents curated instructions as structured steps in a shared JSON format. Both modalities use the same tutorial content, so the comparison focuses on interaction method rather than content differences [25].
Touch users interact through visible controls such as next, previous, materials, search, and overview. Voice users trigger equivalent actions through a constrained speech-recognition pipeline, with visual feedback confirming whether the intended command was recognized and executed.
Tutorials will be selected from public DIY sources and standardized by task length, number of steps, reading complexity, and navigation actions. Implementation work will be managed through a lightweight Scrumban board, which supports prototype development but is not the main research contribution [26].
Participants and Sampling Criteria
The planned sample is 24 participants, split evenly into 12 AB and 12 BA sessions. This size keeps counterbalancing balanced and provides 24 paired observations for each primary comparison, which is appropriate for a supervised exploratory usability evaluation. Participants will be 18-35 years old, familiar with web tutorials, able to perform simple simulated DIY tasks, and not involved in prototype development.
Participants will be excluded if they have expert-level experience in the selected DIY tasks, a temporary voice condition that strongly affects recognition, uncorrected hearing or visual limitations that prevent participation, or an inability to complete the practice task after instruction.
Experimental Tasks and Counterbalancing
Each participant will complete matched hands-busy navigation tasks in both modalities, including following a step, moving forward or backward, reopening materials, repeating an instruction, and finding a specific step. Safe desk-based materials may be used to simulate occupied hands without hazardous tools or substances.
Counterbalancing uses AB/BA order and rotated tutorial sets: one group completes touch before voice, and the other completes voice before touch. Tutorial pairing is reversed across participants to reduce order effects and tutorial-specific memory effects.
Experimental Procedure
Each session follows a script: consent, demographic questionnaire, prototype briefing, short practice in both modalities, first measured condition, SUS, second measured condition, SUS, and brief debriefing. During each measured condition, the system records task time, navigation actions, spoken commands, recognition outcomes, and errors.
Testing Environment and Control Variables
Testing will take place in a controlled quiet environment using the same laptop, browser, screen size, microphone, and internet connection. The browser version and SpeechRecognition support will be logged, the cache and prototype state will be reset between sessions, and microphone recognition will be checked before testing. These controls are important because browser speech recognition can depend on browser and network behavior [24].
The researcher will also log background noise, internet disruption, microphone issues, browser crashes, or recognition interruptions. Trials affected by external technical failure will be marked invalid and repeated only when the issue is clearly unrelated to participant behavior.
Evaluation Metrics and Instruments
Task completion time is measured in seconds from the first interaction to the required completion state. Task success is coded as successful, partially successful, or unsuccessful. SUS is administered after each modality so touch and voice receive separate perceived-usability scores [21], [22].
Voice-only measures are calculated per voice task and then aggregated per participant. Recognition accuracy is the percentage of spoken commands correctly transcribed against the command vocabulary. Command success rate is the percentage of commands that trigger the intended interface action. Recovery effort is the number of repeated commands, rephrased commands, or fallback touch actions needed after recognition or execution failure.
Data Preparation
Interaction logs will be exported as an anonymized dataset containing participant ID, sequence, task set, modality, task time, task success, SUS, command count, recognition outcome, command success, and recovery count. The dataset will be checked for missing values, duplicates, invalid trials, and technical-disruption notes before analysis [27].
Task-time outliers will be inspected using boxplots and z-score or interquartile-range screening. They will be retained unless session notes document an external technical failure, so genuine usability difficulty remains part of the analysis.
